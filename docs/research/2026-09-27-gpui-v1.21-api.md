# API do GPUI na tag v1.21.0 do Zed

Pesquisa de 27/09/2026 para o plano de implementação do protótipo em GPUI. Fonte: clone raso da tag `v1.21.0` de `zed-industries/zed` (commit `33c95853ed2b6956f339733c63a8220964ecbeb6`, 23/09/2026, "v1.21.x stable"). Todo `arquivo:linha` é relativo à raiz do repositório do Zed nessa tag. Nada foi compilado. A resolução de dependências (seção 10) foi medida com `cargo generate-lockfile` e `cargo tree` num projeto-sonda fora do workspace do Zed.

Convenção: "Inferência:" é dedução minha. "Verificado na máquina:" é o que rodei aqui (macOS 27, Xcode 27.0, rustc 1.98.1).

O toolchain do Zed na tag é o Rust `1.98.1` (`rust-toolchain.toml`), edição `2024` (`Cargo.toml:272`).

## 1. `gpui_platform`, acessibilidade e build no macOS

**Corpo das funções** (`crates/gpui_platform/src/gpui_platform.rs`):

```rust
pub fn application() -> gpui::Application {            // :13
    #[cfg(target_family = "wasm")]
    { application_with_web_backend(gpui_web::WebBackendPreference::Auto) }
    #[cfg(not(target_family = "wasm"))]
    gpui::Application::with_platform(current_platform(false))   // :20
}

pub fn headless() -> gpui::Application {               // :23
    gpui::Application::with_platform(current_platform(true))
}

pub fn current_platform(headless: bool) -> Rc<dyn Platform> {   // :57
    #[cfg(target_os = "macos")]
    { Rc::new(gpui_macos::MacPlatform::new(headless)) }         // :60
    // windows / linux / wasm nos demais cfg
}
```

- `MacPlatform::new` exige a main thread: `MainThreadMarker::new().expect("Mac platform not created on main thread")` (`crates/gpui_macos/src/platform.rs:210`).
- `gpui_platform` também expõe `pub fn background_executor() -> gpui::BackgroundExecutor` (`:9`).

**Acessibilidade.** `application()` usa `Application::with_platform`, que NÃO desliga o AccessKit. A árvore fica pronta e só é ativada quando uma tecnologia assistiva (VoiceOver) pede.
- `Application::with_platform(platform: Rc<dyn Platform>) -> Self` (`crates/gpui/src/app.rs:175`).
- `Application::new_inaccessible(platform: Rc<dyn Platform>) -> Self` (`crates/gpui/src/app.rs:192`) põe `accessibility_force_disabled = true` (`:194`). O doc diz que as APIs de acessibilidade "silently no-op" nesse modo (`:186-188`).
- Na criação da janela, se não estiver desligado à força, o GPUI registra callbacks de ativação/desativação no adaptador (`crates/gpui/src/window.rs:1591-1625`). A flag por frame é `active_this_frame = !self.force_disabled && self.active_flag.load(...)` (`crates/gpui/src/window/a11y.rs:213`).
- Não existe API para ligar ou desligar em tempo de execução. O campo `accessibility_force_disabled` é `pub(crate)` (`crates/gpui/src/app.rs:829`). A escolha é só no construtor.
- `gpui_platform` não tem atalho para o modo inacessível. Para desligar: `gpui::Application::new_inaccessible(gpui_platform::current_platform(false))`.

Como o Zed escolhe (`crates/zed/src/main.rs:87-94`):

```rust
fn build_application() -> Application {
    let platform = gpui_platform::current_platform(false);
    if std::env::var("ZED_EXPERIMENTAL_A11Y").as_deref() == Ok("1") {
        Application::with_platform(platform)
    } else {
        Application::new_inaccessible(platform)
    }
}
```

Ou seja, o Zed sai com acessibilidade DESLIGADA por padrão e só liga com `ZED_EXPERIMENTAL_A11Y=1`.

**O que o build exige.**

`crates/gpui_apple/build.rs`:
- Sempre gera `scene.h` com `cbindgen` a partir de fontes do `gpui` (`:26-97`). Acha o `gpui` por caminho relativo: `PathBuf::from(std::env::var("CARGO_MANIFEST_DIR").unwrap()).join("../gpui")` (`:102-104`). Numa dependência git o checkout preserva o layout do repositório, então `../gpui` resolve (verificado na máquina: o checkout do cargo fica em `.../<rev>/crates/gpui_apple`).
- Sem `runtime_shaders`: compila os shaders com `xcrun -sdk macosx metal -gline-tables-only -mmacosx-version-min=10.15.7 -MO -c ...` e `xcrun -sdk macosx metallib ...` (`:126-186`); falha emite `cargo::error=metal shader compilation failed` e `process::exit(1)` (`:157-163`). Isso exige o compilador Metal, que vem com o Xcode, não com as Command Line Tools.
- Com `runtime_shaders`: só concatena `scene.h` + `shaders.metal` em `OUT_DIR/stitched_shaders.metal` (`:108-123`), sem `xcrun`. O renderer compila em tempo de execução com `device.new_library_with_source(&SHADERS_SOURCE_FILE, &metal::CompileOptions::new())` (`crates/gpui_apple/src/metal_renderer.rs:217-220`); sem a feature usa `new_library_with_data(SHADERS_METALLIB)` (`:221-224`).
- `crates/media/build.rs` (dependência de `gpui_macos`) roda `xcrun --sdk macosx --show-sdk-path` e `bindgen` sobre `src/bindings.h` (`:6-35`). O `bindgen` precisa de `libclang` em tempo de build. `crates/media/Cargo.toml` declara `bindgen = "0.72"` em `[build-dependencies]`.
- O `gpui` também declara `bindgen = "0.72"` como build-dependency no macOS (`crates/gpui/Cargo.toml:161-162`), mas o `build.rs` dele não usa (`crates/gpui/build.rs`, só trata `windows-manifest`).
- O README pede Xcode completo, aberto uma vez, e `xcode-select --switch /Applications/Xcode.app/Contents/Developer` (`crates/gpui/README.md:54-72`).

Verificado na máquina: `xcode-select -p` aponta para `/Applications/Xcode.app/Contents/Developer` (Xcode 27.0), mas `xcrun -sdk macosx metal --version` falha com `cannot execute tool 'metal' due to missing Metal Toolchain; use: xcodebuild -downloadComponent MetalToolchain`, e `xcrun -f metallib` não acha a ferramenta. Então o build padrão (sem `runtime_shaders`) falha aqui até rodar `xcodebuild -downloadComponent MetalToolchain`. `libclang.dylib` existe tanto no Xcode quanto nas CLT.

## 11. Timer: tolerância ou `dispatch_after`

Só `dispatch_after`, sem leeway.
- `BackgroundExecutor::timer` (`crates/gpui/src/executor.rs:183-188`) chama `self.spawn(self.inner.scheduler().timer(duration))`.
- `PlatformScheduler::timer` (`crates/gpui/src/platform_scheduler.rs:129-151`) monta um runnable que só faz `tx.send(())` e o agenda com `dispatcher.dispatch_after(duration, runnable)` (`:145`); devolve `Timer::new(rx)`.
- No macOS (`crates/gpui_macos/src/dispatcher.rs:64-73`):
  ```rust
  fn dispatch_after(&self, duration: Duration, runnable: RunnableVariant) {
      let context = runnable.into_raw().as_ptr() as *mut c_void;
      let queue = DispatchQueue::global_queue(GlobalQueueIdentifier::Priority(
          DispatchQueueGlobalPriority::High,
      ));
      let when = DispatchTime::NOW.time(duration.as_nanos() as i64);
      unsafe { DispatchQueue::exec_after_f(when, &queue, context, trampoline); }
  }
  ```
- O trait `PlatformDispatcher` (`#[doc(hidden)]`) só tem `fn dispatch_after(&self, duration: Duration, runnable: RunnableVariant);` (`crates/gpui/src/platform.rs:1124-1131`). Não há parâmetro de tolerância nem de leeway, e o grep por `leeway`, `DispatchSource`, `NSTimer` e `CFRunLoopTimer` em `gpui`, `gpui_macos`, `gpui_apple` e `scheduler` não achou nada.
- Inferência: um timer esperado dentro de `cx.spawn` dá dois saltos: dispara na fila global High e acorda a task em primeiro plano, que volta à main queue (`dispatch_on_main_thread`, `dispatcher.rs:57-62`).

Coisas vizinhas úteis para o player:
- `BackgroundExecutor::prevent_app_nap(&self, reason: &str) -> ActivityGuard` (`executor.rs:94-97`) usa `NSActivityOptions::UserInitiatedAllowingIdleSystemSleep` (`dispatcher.rs:82-87`).
- `Priority::RealtimeAudio` ("Only use for audio", `crates/scheduler/src/scheduler.rs:32-34`) roda em thread própria via `spawn_realtime`, com `THREAD_TIME_CONSTRAINT_POLICY` (período de 2,9 ms, `dispatcher.rs:75-80`, `:113-196`). Não pode passar por `dispatch` (`panic!`, `dispatcher.rs:43-45`).
